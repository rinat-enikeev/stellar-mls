Proof of Correctness

Evidence that the code correctly implements the zero-knowledge group membership protocol. Version 1.0 — April 7, 2026.

This document proves that the SEP-XXXX reference implementation is correct: the code faithfully realizes the protocol specified in the SEP. This is complementary to the Proof of Soundness, which proves that the mathematical constructions are secure. A secure protocol implemented incorrectly is insecure. Both documents are necessary for end-to-end assurance.

1. Preamble

Scope

This document provides a systematic correctness argument for the SEP-XXXX reference implementation. It proves that the code faithfully implements the protocol specified in the SEP specification.

In scope. Functional correctness of the core Rust library, FFI bridges (C and JNI), Soroban smart contract, relayer, PN-Relay, and mobile clients. Cross-platform determinism. Protocol conformance against the SEP specification.

Out of scope. Cryptographic security reductions (covered by the Proof of Soundness), performance optimization arguments, deployment procedures, and network-layer privacy analysis.

Relationship to Proof of Soundness

The two documents form a layered assurance argument:

LayerDocumentQuestion Answered
Mathematical securityProof of SoundnessAre the cryptographic constructions secure?

Each theorem in the Proof of Soundness depends on implementation assumptions. For example, Theorem 1 (Merkle Tree Collision Resistance) assumes that the implementation uses the Poseidon hash function with the specified parameters and constructs the tree at the specified depth with zero-padded leaves. Section 5 of this document maps each theorem to the code that realizes its assumptions.

2. Correctness Model

Definition of Implementation Correctness

An implementation is correct with respect to a specification if, for all inputs in the specification's domain:

  1. Functional equivalence. The implementation's outputs match the specification's defined outputs.
  2. Constraint adherence. The implementation enforces all constraints and invariants required by the specification.
  3. Cross-platform determinism. All platform-specific implementations (Rust, iOS via FFI, Android via JNI) produce identical outputs for identical inputs.
  4. Failure mode correctness. The implementation rejects all inputs that the specification defines as invalid.

2.1 Correctness Properties

The following 14 properties collectively define what it means for the implementation to be correct. Each property is traced to specific code, specification sections, and tests in Sections 3–6.

Property C-1 — Poseidon Parameters

Seed string, round counts (8 full, 56 partial), MDS matrix construction, and alpha exponent (5) match SEP-XXXX Section 2.2.

Property C-2 — Poseidon Determinism

poseidon_hash_one and poseidon_hash_two are deterministic pure functions: identical inputs always produce identical outputs.

Property C-3 — Leaf Computation

Each leaf is computed as Poseidon(sk) where sk is the member's BLS12-381 private key scalar.

Property C-4 — Member Ordering

Members are sorted in ascending lexicographic order by their 48-byte compressed G1 public key representation; duplicates are rejected.

Property C-5 — Merkle Tree Construction

Binary tree of fixed depth d ∈ {5, 8, 11}, zero-padded unused leaves, internal nodes computed as Poseidon(left, right).

Property C-6 — Commitment Variant B

Poseidon(Poseidon(root, epoch), salt) where salt is interpreted as a field element via from_le_bytes_mod_order.

Property C-7 — Commitment Variant A

SHA-256(root_be || epoch_be || salt) with fixed 72-byte preimage (32 + 8 + 32).

Property C-8 — Circuit Constraints

Exactly 3 logical constraints (key ownership, Merkle membership, commitment binding) with 2 public inputs (commitment, epoch).

Property C-9 — Proof Format

192 bytes compressed: G1 (48 bytes) || G2 (96 bytes) || G1 (48 bytes). 384 bytes uncompressed for on-chain submission.

Property C-10 — Epoch Enforcement

new_epoch == stored_epoch + 1 enforced by the contract with checked_add overflow protection.

Property C-11 — Proof Replay Prevention

SHA-256 hash of uncompressed proof components (384 bytes) stored and checked before every state-changing operation.

Property C-12 — Groth16 Pairing

Verification equation e(-piA, piB) · e(alpha, beta) · e(vk_x, gamma) · e(piC, delta) = 1_GT implemented via Soroban BLS12-381 host functions.

Property C-13 — FFI Canonicality

Field elements received from C/JNI callers are checked for canonical form (value < field modulus) via roundtrip encoding; non-canonical values are rejected.

Property C-14 — Cross-Platform Determinism

Given identical inputs, the Rust library, iOS FFI, and Android JNI produce byte-identical outputs (leaf hashes, roots, commitments, proofs).

2.2 Cross-Component Invariants

These invariants span module boundaries and must hold throughout any execution path.

INV-1 — Commitment Pipeline Consistency

The commitment computed by compute_poseidon_commitment() outside the circuit equals the value computed by the circuit's Constraint 3 for the same inputs. Components: Poseidon, Merkle, Commitment, Circuit.

INV-2 — Proof Decompression Format

The 192-byte compressed proof produced by proof_to_bytes() decompresses to the same 384-byte representation expected by the Soroban contract. Components: Prover, FFI, Contract.

INV-3 — Epoch Chain Monotonicity

The contract enforces strict epoch + 1 sequencing; the relayer does not interfere with this invariant. Components: Contract, Relayer.

INV-4 — Key Consistency Across Platforms

BLS12-381 secret key bytes interpreted by the C FFI, JNI FFI, iOS, and Android all produce the same field element. Components: FFI (C), FFI (JNI), iOS, Android.

INV-5 — Leaf Consistency Across Platforms

Poseidon(sk) computed via the C FFI equals Poseidon(sk) computed via the JNI FFI for the same sk bytes. Components: Poseidon, FFI (C), FFI (JNI).

INV-6 — Root Consistency Across Platforms

Given the same member set, the Merkle root computed via C FFI equals the root computed via JNI FFI. Components: Merkle, FFI (C), FFI (JNI).

INV-7 — Relayer Transparency

The relayer wraps and submits transactions but does not modify proof bytes, public inputs, or group identifiers. Components: Relayer, Contract.

INV-8 — PN-Relay Confidentiality

The PN-Relay cannot read the content of encrypted Nostr events; it only observes topic tags for notification routing. Components: PN-Relay, Nostr.

3. Module-by-Module Arguments

Each module's correctness argument combines code inspection, specification tracing, and empirical evidence from the test suite. Below are the five core modules.

3.1 Poseidon Hash

Source. src/poseidon/mod.rs (283 lines)

Implements the Poseidon hash function over the BLS12-381 scalar field with the parameters specified in SEP-XXXX Section 2.2. Provides two entry points: poseidon_hash_one(config, x) for leaf hashing and poseidon_hash_two(config, left, right) for internal Merkle nodes and commitment binding.

Claim — Poseidon Correctness

Parameter fidelity (C-1). The constants FULL_ROUNDS = 8, PARTIAL_ROUNDS = 56, RATE = 2, CAPACITY = 1, ALPHA = 5 match SEP-XXXX Section 2.2 verbatim.

Round constant derivation (C-1). generate_round_constants() uses seed "SEP-XXXX-Poseidon-BLS12-381-w3-f8-p56-a5-round-constants" and derives 192 constants via iterated SHA-256 with 64-byte extension for uniform field element sampling.

MDS matrix (C-1). generate_mds_matrix() implements the Cauchy construction M[i][j] = 1 / (x_i + y_j) with x_i = i + 1, y_j = width + j + 1.

Determinism (C-2). Both hash functions are pure: they allocate a fresh PoseidonSponge, absorb inputs, and squeeze output. No mutable state persists between calls.

Test coverage. 11 tests: config creation, determinism, hash non-triviality, distinct inputs yield distinct outputs, round constant count, and MDS matrix invertibility.

3.2 Merkle Tree

Source. src/merkle/mod.rs (536 lines)

Constructs a binary Poseidon Merkle tree of fixed depth from a set of member records. Provides canonical ordering, tree construction, root computation, and opening proof generation/verification.

Claim — Merkle Correctness

Canonical ordering (C-4). canonicalize_members() sorts members by 48-byte compressed G1 public key bytes in ascending lexicographic order. Duplicates are detected and rejected with MerkleError::DuplicatePublicKey.

Leaf computation (C-3). Each leaf is poseidon_hash_one(config, sk), matching SEP-XXXX Section 2.2.

Tree construction (C-5). Creates a flat array of 2^(d+1) nodes. Leaves at indices [2^d, 2^(d+1)). Unused slots are F::zero(). Internal nodes computed bottom-up as poseidon_hash_two(config, left, right). Root at index 1.

Depth enforcement (C-5). Member sets exceeding 2^depth are rejected via TooManyMembers error.

Test coverage. 20 tests: single-member trees, full trees, zero padding, opening proofs, canonical ordering (shuffled inputs produce same root), duplicate rejection, depth overflow.

3.3 Circuit

Source. src/circuit/mod.rs (785 lines)

Defines the R1CS circuit for Groth16 proving. MembershipCircuit implements ConstraintSynthesizer<Fr>, generating constraints for key ownership, Merkle membership, and commitment binding.

Claim — Circuit Correctness

Public inputs (C-8). Exactly two values allocated as public inputs via FpVar::new_input(): commitment_var and epoch_var. All other values are witnesses.

Constraint 1 — Key ownership. Computes leaf = poseidon_hash_one_gadget(cs, config, sk), the in-circuit equivalent of Poseidon(sk).

Constraint 2 — Merkle membership. Iterates over d levels using FpVar::conditionally_select() for ordering, then poseidon_hash_two_gadget() for parent computation. Asserts current == root.

Constraint 3 — Commitment binding. Computes Poseidon(Poseidon(root, epoch), salt) via two poseidon_hash_two_gadget() calls and asserts equality with the public commitment.

Test coverage. 18 tests: circuit satisfiability, constraint count per tier (1910, 2630, 3350), rejection of wrong secret key/path/salt/epoch/commitment, public input count (exactly 2).

3.4 Smart Contract

Source. contracts/sep-xxxx/src/lib.rs (1953 lines)

Soroban smart contract that stores group commitments and verifies Groth16 membership proofs on-chain using BLS12-381 host functions.

Claim — Contract Correctness

Epoch enforcement (C-10). update_commitment() uses checked_add(1) with strict equality check. Rejects any epoch value other than stored_epoch + 1.

Proof replay prevention (C-11). proof_hash() computes SHA-256(piA || piB || piC) from 384 uncompressed bytes. Hash is stored after verification and checked before every state-changing call.

Groth16 verification (C-12). Computes vk_x = IC[0] + commitment · IC[1] + epoch · IC[2] via g1_msm(), negates piA, and calls bls.pairing_check() to verify the pairing equation.

Canonical input validation (C-13). Roundtrip check rejects non-canonical field element encodings.

Deactivation permanence. deactivate_group() sets active = false irreversibly; subsequent updates are rejected.

Test coverage. 56 tests: initialization, epoch transitions (valid/invalid), public input mismatches, proof replay rejection, deactivation, tier limits, VK validation, history window, TTL bumping.

3.5 FFI Bridges

Sources. src/ffi.rs (C bridge, 1235 lines) and src/jni_ffi.rs (JNI bridge, 418 lines)

Both bridges follow the same pattern: read input buffers, deserialize to Rust types, call core library, serialize output, write to output buffer. Errors are communicated via C error strings or Java exceptions respectively.

Claim — FFI Correctness

Panic safety. Every exported function is wrapped in run_ffi() / run_jni(), which catches panics via std::panic::catch_unwind(). Unwinding across the FFI boundary is undefined behavior; these wrappers prevent it.

Canonicality enforcement (C-13). read_fr() calls bytes_be_to_field_checked(), rejecting non-canonical field element encodings. Secret keys use Fr::from_be_bytes_mod_order() without the canonical check (correct: any valid scalar works for private witnesses).

Structural equivalence. Both C and JNI bridges call the same core library functions. The only difference is the marshalling layer, ensuring INV-4, INV-5, and INV-6.

Buffer management. C FFI transfers ownership via mem::forget() with corresponding sep_free_buffer(). Length validation via require_len() occurs before any deserialization.

Test coverage. 34 C FFI tests + ~50 Android instrumented tests covering: all exported functions, null pointer handling, wrong-length inputs, non-canonical rejection, panic recovery, memory lifecycle.

4. Cross-Platform Consistency

4.1 Architecture

All three platforms (Rust, iOS, Android) execute the same compiled Rust code. iOS uses C-linkage FFI with a static library. Android uses JNI with a shared library. The FFI/JNI layers perform only serialization/deserialization with no mathematical operations.

Key principle: All cryptographic operations are implemented exactly once, in Rust. Platform-specific code only handles marshalling. This architectural constraint is the primary guarantee of cross-platform determinism.

4.2 Serialization Convention

All values cross the FFI boundary as byte arrays with defined endianness: big-endian for field elements (via field_to_bytes_be() and bytes_be_to_field_checked()). Neither the Swift nor Kotlin side performs mathematical operations on these bytes — they pass them opaquely to and from the Rust layer.

4.3 Determinism Claim

Property C-14 — Cross-Platform Determinism (Detailed)

For identical inputs (secret keys, member rosters, salts, epochs), the following outputs are byte-identical across Rust, iOS/C FFI, and Android/JNI:

  • Poseidon leaf hashes
  • Merkle roots
  • Poseidon commitments (Variant B)
  • SHA-256 commitments (Variant A)
  • Groth16 proofs (given the same RNG seed)
  • Proof serializations (192-byte and 384-byte formats)

Evidence. The cross-platform test vectors (docs/cross-platform-test-vectors.json) define expected outputs for specific inputs. These vectors are validated independently on each platform. The two cross-platform tests in tests/cross_platform_tests.rs provide additional validation.

7. Known Limitations

  1. No formal verification. This document provides a structured argument, not a machine-checked proof. The correctness claims depend on manual code inspection and empirical testing.
  2. Trusted setup simulation. The reference implementation's key derivation uses a simulation approach where ceremony scalars are hashed into a CSPRNG seed. Production deployments require Phase 2 MPC key derivation.
  3. arkworks dependency. Poseidon hash, Groth16 prover/verifier, and BLS12-381 arithmetic are provided by the arkworks library suite. This document does not prove the correctness of arkworks itself.
  4. Soroban host function opacity. The contract's Groth16 verification depends on Soroban's bls12_381_g1_msm, bls12_381_pairing_check, and related host functions. Their correctness is an assumption of the Stellar protocol.
  5. Cross-platform test vector coverage. The cross-platform test vectors cover a representative but not exhaustive set of inputs. Edge cases near the modulus boundary are tested in module-specific tests but not all appear in the cross-platform vectors.
  6. Post-compromise forward secrecy. As established by Theorem 8 of the Proof of Soundness, the symmetric protocol cannot cryptographically evict removed members. This is a protocol design limitation, not an implementation bug.
