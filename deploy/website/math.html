Proof of Soundness

Formal mathematical proofs for the SEP-XXXX zero-knowledge group membership protocol. Version 1.0 — April 6, 2026.

This document proves that Onym's cryptographic protocol is sound: only real members can prove membership, proofs reveal nothing about the prover, and on-chain state cannot be forked or replayed. Eight theorems compose into a complete security argument.

1. Preamble

Scope

This document provides formal security proofs for the SEP-XXXX zero-knowledge group membership protocol as implemented in the Onym system. We prove eight theorems establishing:

  1. Membership soundness — only holders of a secret key in the committed member set can produce an accepting proof.
  2. Membership privacy — the proof reveals nothing about the prover's identity or position.
  3. Commitment confidentiality — on-chain commitments reveal no membership information.
  4. State integrity — group state advances monotonically and cannot be forked.
  5. Proof non-replayability — an accepted proof cannot be replayed.
  6. Fee-payer unlinkability — the relayer pattern decouples submitter from prover.

We also reproduce the impossibility proof for symmetric member removal from the fourth security audit.

Out of scope. Network-layer traffic analysis, side-channel attacks on client implementations, and denial-of-service attacks.

Protocol Version

This analysis covers Variant B (Poseidon-only commitment) of SEP-XXXX:

commitment = H_P(H_P(root, epoch), salt)

2. System Model

Definition 2.1 — Group State

A group state is a tuple (G, C, e, t) where G = {sk_1, …, sk_n} ⊂ F_r is the member set, C ∈ F_r is the on-chain commitment, e ∈ N is the epoch (starting at 0), and t ∈ {0, 1, 2} is the tier determining tree depth d ∈ {5, 8, 11}.

Definition 2.2 — Membership Predicate

M(sk, G, C, e) = 1 iff: (1) sk ∈ G, (2) root is the Poseidon Merkle root of G under canonical ordering, and (3) there exists salt s ∈ F_r such that C = H_P(H_P(root, e), s).

Definition 2.3 — Adversary Model

PPT adversary A with oracle access to: CreateGroup, UpdateCommitment, VerifyMembership (public contract calls), Corrupt(i) → reveals sk_i (adaptive corruption), and Observe(relay) → sees encrypted events, timing, topic tags.

Definition 2.4 — Security Goals

Five security games: SND (soundness — forge a proof without knowing any sk ∈ G), ZK (zero-knowledge — distinguish real from simulated proofs), HIDE (commitment hiding — recover root from commitment), EPOCH (epoch integrity — revert, skip, or fork epochs), PRIV (prover privacy — identify which member produced a proof).

Definition 2.5 — Canonical Member Ordering

For each sk_i, compute compressed BLS12-381 G1 public key pk_i = [sk_i] · G_1 (48 bytes). Sort by lexicographic big-endian order. Reject duplicates. This ensures any permutation of the same set produces the same Merkle tree.

3. Cryptographic Assumptions

Assumption 3.1 — Poseidon Preimage Resistance

For H_P with width 3, 8 full rounds, 56 partial rounds, α = 5 over BLS12-381 F_r: AdvPreH_P(A) ≤ negl(λ). Justified by Grassi et al. (USENIX Security 2021) with ≥2x safety margin over minimum rounds.

Assumption 3.2 — Poseidon Collision Resistance

AdvCRH_P(A) = Pr[(x, x') ← A : x ≠ x' ∧ H_P(x) = H_P(x')] ≤ negl(λ). The parameters provide ≥128-bit security against all known collision-finding attacks.

Assumption 3.3 — Groth16 Knowledge Soundness

Under the q-SDH and Knowledge of Exponent assumptions over BLS12-381: for any PPT prover producing an accepting proof, there exists an extractor that outputs a valid witness with overwhelming probability (Groth, EUROCRYPT 2016).

Assumption 3.4 — Groth16 Zero-Knowledge

Groth16 provides perfect zero-knowledge: there exists a simulator S producing proofs identically distributed to honest proofs given only public inputs and the simulation trapdoor.

Assumption 3.5 — BLS12-381 Pairing Security

The co-CDH and q-SDH assumptions hold. Embedding degree 12 provides ≥128-bit discrete logarithm security in G_T.

Assumption 3.6 — HKDF-SHA256 PRF Security

HKDF-SHA256 (RFC 5869) is a secure PRF family: AdvPRFHKDF(D) ≤ negl(λ).

Assumption 3.7 — AES-256-GCM Security

AES-256-GCM provides IND-CPA and INT-CTXT security under unique nonces.

Assumption 3.8 — Trusted Setup Integrity

At least 1-of-N participants in the MPC ceremony is honest. Under this assumption, the simulation trapdoor is unknown and the CRS is indistinguishable from one generated by a trusted dealer.

4. Theorem 1: Merkle Tree Collision Resistance

Theorem 1

For any PPT adversary A, the probability of finding two distinct canonically-ordered member sets S_1 ≠ S_2 such that MerkleRoot(S_1) = MerkleRoot(S_2) is negligible in λ, assuming Poseidon collision resistance (Assumption 3.2).

Proof

Construction. Given canonically-ordered member set S = {sk_1, …, sk_n} with n ≤ 2d, the Merkle tree T of depth d is:

  1. Compute leaf hashes: l_i = H_P(sk_i) for i = 1, …, n.
  2. Pad with zeros: l_i = 0 for i = n+1, …, 2d.
  3. For each internal node (bottom-up): T[j] = H_P(T[2j], T[2j+1]).
  4. Root is T[1].

Reduction. Suppose A outputs (S_1, S_2) with S_1 ≠ S_2 and equal roots. We build adversary B that breaks Poseidon CR:

B builds both trees. Since S_1 ≠ S_2, the leaf layers differ. Walking from the root (where T_1[1] = T_2[1]) downward, there must exist a node j* where T_1[j*] = T_2[j*] but its children differ: (T_1[2j*], T_1[2j*+1]) ≠ (T_2[2j*], T_2[2j*+1]). This yields a Poseidon collision.

Bound. The tree has at most 2d+1 - 1 internal nodes:

Adv^TreeCR(A) ≤ (2^(d+1) - 1) · Adv^CR_H_P(B)

For d = 11: ≤ 4095 · AdvCRH_P(B), which remains negligible.

■

Corollary 4.1 — Canonical Injectivity

Distinct canonically-ordered member sets produce distinct Merkle roots with overwhelming probability.

Remark 4.2 (Zero-Padding Security). Empty leaf slots use l = 0 ∈ F_r. Forging membership at an empty slot requires finding sk* such that H_P(sk*) = 0, which contradicts Assumption 3.1. The implementation verifies H_P(0) ≠ 0.

5. Theorem 2: Commitment Hiding

Theorem 2

Given commitment C = H_P(H_P(root, e), s) where s is uniform random over {0,1}256 reduced mod r, no PPT adversary observing (C, e) can recover root with probability better than AdvPreH_P(A) + 1/|F_r|.

Proof

Salt entropy. Since r < 2256, reduction mod r maps at most 2 preimages per output, giving min-entropy H_∞(s) ≥ 254 bits — well above the 128-bit security level.

Game 1. The commitment C = H_P(h, s) where h = H_P(root, e). Since salt s is unknown with 254 bits of min-entropy, recovering h requires either guessing s (probability ≤ 1/|F_r| ≈ 2-255) or inverting H_P (contradicting Assumption 3.1).

Game 2. Even if h is recovered, extracting root from h = H_P(root, e) requires a second preimage inversion.

Union bound:

Pr[A recovers root] ≤ Adv^Pre_H_P(A) + 1/|F_r|

Both terms are negligible.

■

Corollary 5.1 — Commitment Unlinkability

Two commitments with independently sampled salts are computationally indistinguishable even for the same member set at different epochs.

6. Theorem 3: ZK Membership Soundness

Theorem 3

If the Groth16 verification equation accepts proof π for public inputs (C, e), then the prover knows a witness (sk, root, s, path, idx) satisfying all three circuit constraints, except with probability negligible in λ.

Proof

Step 1: Knowledge extraction. By Groth16 knowledge soundness (Assumption 3.3), there exists an extractor E that outputs a valid witness with overwhelming probability.

Step 2: Witness validity. The extracted witness satisfies three constraints simultaneously:

Constraint 1 — Key Ownership: l = H_P(sk). The prover knows sk whose hash equals leaf l.

Constraint 2 — Merkle Membership: Starting from l at index idx, the path of sibling hashes leads to root:

current_0 = l
current_{i+1} = H_P(current_i, path[i])   if idx[i] = 0
              = H_P(path[i], current_i)    if idx[i] = 1
current_d = root

Constraint 3 — Commitment Binding: H_P(H_P(root, e), s) = C.

Step 3: Composition. By Theorem 1, the root uniquely determines the member set. By Constraint 1, sk belongs to that set. By Constraint 3, this is the set committed on-chain at epoch e. Therefore, the prover is a member of the committed group.

■

Remark 6.1. Groth16 provides knowledge soundness (argument of knowledge), which is stronger than plain soundness. A valid proof guarantees the prover knows a secret key — not merely that one exists.

7. Theorem 4: Zero-Knowledge Property

Theorem 4

The proof π reveals no information about the witness (sk, root, s, path, idx) beyond the public inputs (C, e).

Proof

By Groth16 perfect zero-knowledge (Assumption 3.4), there exists a simulator S producing proofs identically distributed to honest proofs given only public inputs and the simulation trapdoor. This is information-theoretic, not merely computational.

Hidden: sk (which member), idx (position in tree), path (tree structure), s (salt), root (Merkle root).

Observable: C (opaque commitment, hidden by Theorem 2) and e (epoch number).

■

Corollary 7.1 — Constant-Size Proofs

A Groth16 proof consists of π = (π_A ∈ G_1, π_B ∈ G_2, π_C ∈ G_1). Compressed: 48 + 96 + 48 = 192 bytes, regardless of group size. No side-channel on |G|.

Corollary 7.2 — Multi-Proof Unlinkability

Given two proofs for the same commitment C, a verifier cannot determine whether they were produced by the same or different members. Both are simulatable without any witness.

8. Theorem 5: Epoch Monotonicity and State Integrity

Theorem 5

Under the contract's epoch enforcement (new_epoch == stored_epoch + 1), no adversary can: (a) revert to a previous epoch, (b) skip an epoch, or (c) fork the group state.

Proof

(a) No reversion. The contract enforces strict equality: new_epoch == current.epoch + 1. Any new_epoch ≤ current.epoch is rejected. Overflow is prevented by checked_add.

(b) No skipping. The same strict equality prevents any value other than current.epoch + 1.

(c) No forking. The contract stores exactly one CommitmentEntry per group_id. Two competing updates at epoch e both require proofs against (C_e, e). Stellar's deterministic transaction ordering ensures exactly one executes first, advancing to e+1. The second fails because current.epoch is now e+1, not e.

Inductive argument. Base case: group creation requires epoch = 0 and a valid membership proof. Inductive step: update_commitment verifies a proof against the current commitment — the updater must be a current member — before storing the new state.

■

Remark 8.1 (Deactivation). deactivate_group sets active = false irreversibly. Subsequent updates are rejected. verify_membership remains available for historical queries.

9. Theorem 6: Proof Non-Replayability

Theorem 6

A proof π accepted for one state-changing contract call cannot be replayed to any other state-changing call.

Proof

Proof hash. For each proof π = (π_A, π_B, π_C), the contract computes:

h_π = SHA-256(π_A || π_B || π_C)    // 96 + 192 + 96 = 384 bytes

Recording. After successful verification in any state-changing function, h_π is stored persistently.

Checking. Before verification, every state-changing function rejects if h_π already exists.

Cross-function: The hash is function-independent — a proof accepted by create_group cannot be resubmitted to update_commitment.

Cross-group: The proof is bound to specific public inputs (C, e). A different group with C' ≠ C would fail Groth16 verification. The hash check provides a second defense layer.

Collision resistance: Distinct proofs π ≠ π' with h_π = h_π' would constitute a SHA-256 collision.

Read-only exception: verify_membership does not record the hash, allowing reuse for read-only queries.

■

10. Theorem 7: Fee-Payer Privacy

Theorem 7

If a relayer submits transactions on behalf of group members, the on-chain record reveals only the relayer's Stellar account — not the prover's identity.

Proof

Transaction structure. A Stellar transaction contains source_account (the relayer), operations, fee, and signature. None contain the prover's identity.

Contract authorization. update_commitment accepts (group_id, new_commitment, new_epoch, proof, public_inputs) — no caller address parameter. Authorization is proof-only.

Proof zero-knowledge. By Theorem 4, the proof reveals nothing about the prover.

Formal bound:

Adv^Identify(A) = Adv^ZK(A) + Adv^Network(A)

where AdvZK(A) ≤ negl(λ) and AdvNetwork(A) captures IP-based deanonymization (out of scope).

Residual leakage: Timing correlation at the relayer's HTTPS endpoint is a network-layer concern, mitigated by Tor, VPN, or batching.

11. Theorem 8: Symmetric Member Removal Impossibility

Theorem 8 (from Security Audit v4)

No modification to the symmetric-key-only key derivation protocol can provide cryptographic eviction of a removed member who retains the group secret. For any KDF computing K_{e+1} = KDF(groupSecret, e+1, s_{e+1}, aux) where aux is derivable from shared state, a removed member M_r who knows (groupSecret, K_e) can compute K_{e+1}.

Proof

Setup. Group with members {M_1, …, M_n} sharing: groupSecret, traffic key K_e = HKDF(groupSecret || e || s_e), epoch e, salt s_e. Member M_r is removed at epoch e.

Observation 1. The removal message must be encrypted under K_e (the current key). It contains e+1 and s_{e+1} so remaining members can derive K_{e+1}.

Observation 2. At removal, M_r possesses: (1) groupSecret, (2) K_e, (3) the removal message (decryptable with K_e, yielding e+1 and s_{e+1}), and (4) the member roster.

Observation 3. K_{e+1} = HKDF(groupSecret || (e+1) || s_{e+1}) — all inputs are known to M_r.

Generalization by exhaustion. Six natural "fixes" all fail:

  1. Omitting salt — remaining members can't derive the key either.
  2. Deterministic salt from groupSecret — M_r computes it too.
  3. Transition key from K_e — M_r knows K_e.
  4. Salt as function of member set — member set is public after removal.
  5. Chained KDF rounds — all intermediates computable from same inputs.
  6. Epoch-dependent KDF with removal flag — flag is observable.

Principle: Any deterministic function of values all known to M_r is computable by M_r.

■

Corollary 11.1 — Necessity of Asymmetric Rekey

Secure removal requires delivering a secret only to remaining members via per-recipient X25519 inbox encryption. This transforms the protocol into a hybrid symmetric-asymmetric system where the asymmetric component provides key separation.

12. Overall System Soundness

Composing Theorems 1–8, the SEP-XXXX protocol provides: membership soundness (Thm 3 + 1), membership privacy (Thm 4), state integrity (Thm 5 + 6), commitment confidentiality (Thm 2), and fee-payer unlinkability (Thm 7).

12.1 Membership Soundness

Only holders of a secret key in the committed set can produce an accepting proof. By Theorem 3, an accepting proof implies knowledge of a valid witness. By Theorem 1, the root uniquely determines the member set.

12.2 Membership Privacy

A verifier learns nothing about the prover's identity. By Theorem 4 (perfect ZK), Corollary 7.1 (constant proof size), and Corollary 7.2 (multi-proof unlinkability).

12.3 State Integrity

Group state advances correctly and cannot be forked or reverted. By Theorem 5 (epoch monotonicity) and Theorem 6 (proof non-replayability).

12.4 Commitment Confidentiality

On-chain commitments reveal no membership information. By Theorem 2 (commitment hiding) and Corollary 5.1 (unlinkability across epochs).

12.5 Fee-Payer Unlinkability

Transaction submitter is decoupled from prover. By Theorem 7 and Theorem 4.

Acknowledged Limitations

  1. Post-compromise forward secrecy — Theorem 8 shows the symmetric protocol cannot evict removed members. Requires asymmetric rekey (Corollary 11.1).
  2. Group size upper bound — Tier t ∈ {0, 1, 2} is on-chain, leaking an upper bound (32, 256, or 2,048). Information-theoretic; cannot be eliminated without a universal circuit.
  3. Network-layer privacy — Nostr relay traffic analysis is out of scope for the cryptographic protocol.
  4. Trusted setup — If all N ceremony participants are dishonest, soundness is lost (Assumption 3.8).

Round Constant Derivation

192 constants derived deterministically via iterated SHA-256:

seed_0 = SHA-256("SEP-XXXX-Poseidon-BLS12-381-w3-f8-p56-a5-round-constants")

For i = 0, 1, ..., 191:
    extended[0..32]  = seed
    seed = SHA-256(seed)
    extended[32..64] = seed
    seed = SHA-256(seed)
    constant_i = Fr::from_le_bytes_mod_order(extended[0..64])

The 192 constants are arranged as 64 rounds of 3 constants each.

MDS Matrix (Cauchy)

The 3×3 MDS matrix M is:

M[i][j] = 1 / (x_i + y_j)

where x_i = i + 1, y_j = w + j + 1  for i, j ∈ {0, 1, 2}

M = | 5^-1  6^-1  7^-1 |
    | 6^-1  7^-1  8^-1 |
    | 7^-1  8^-1  9^-1 |

All inverses in F_r. The Cauchy construction guarantees every square submatrix is invertible (MDS property).

Security Margins

Minimum rounds for known attacks: ~6 (algebraic), ~4 (interpolation), ~6 (differential/linear). With 8 full + 56 partial rounds, the design provides approximately 2x safety margin.

Appendix B: Groth16 Verification Equation

Pairing Equation

e(-π_A, π_B) · e(α, β) · e(vk_x, γ) · e(π_C, δ) = 1_G_T

where vk_x = IC[0] + C · IC[1] + e · IC[2]

with C ∈ F_r (commitment, public input 1), e ∈ F_r (epoch, public input 2), and IC[0..2] ∈ G_1 (verification key input commitment points).

Canonical Input Validation

The contract validates that commitment bytes represent a canonical field element (integer value < r), preventing malleability from non-canonical encodings. Epoch (u64) is padded to 256-bit big-endian, which is always canonical since all u64 values are < r.

Appendix C: Contract Pseudocode

create_group

function create_group(group_id, commitment, tier, proof, public_inputs):
    require(tier ≤ 2)
    require(!storage.has(Group(group_id)))
    require(public_inputs.commitment == commitment)
    require(public_inputs.epoch == 0)

    check_proof_replay(proof)
    vk = load_vk(tier)
    require(verify_groth16_proof(vk, proof, commitment, 0))
    record_proof(proof)

    store CommitmentEntry { commitment, epoch: 0, active: true }
    require(tier_count < 10,000)

update_commitment

function update_commitment(group_id, new_commitment, new_epoch, proof, public_inputs):
    current = storage.get(Group(group_id))
    require(current.active)
    require(new_epoch == current.epoch + 1)            // strict monotonicity
    require(public_inputs.commitment == current.commitment)  // bind to CURRENT state
    require(public_inputs.epoch == current.epoch)

    check_proof_replay(proof)
    vk = load_vk(tier)
    require(verify_groth16_proof(vk, proof, current.commitment, current.epoch))
    record_proof(proof)

    current.commitment = new_commitment
    current.epoch = new_epoch

deactivate_group

function deactivate_group(group_id, proof, public_inputs):
    current = storage.get(Group(group_id))
    require(current.active)
    require(public_inputs matches current state)

    check_proof_replay(proof)
    verify proof against current state
    record_proof(proof)

    current.active = false    // irreversible

Proof Replay Prevention

function proof_hash(proof):
    return SHA-256(π_A || π_B || π_C)    // 384 bytes uncompressed

function check_proof_replay(proof):
    h = proof_hash(proof)
    require(!storage.has(UsedProof(h)))

function record_proof(proof):
    h = proof_hash(proof)
    storage.set(UsedProof(h), true)
