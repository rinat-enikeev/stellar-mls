# Breaking-Changes Release Process

Checklist for shipping a new `StellarChat` / `Onym` version when the Soroban contract ABI, the circuit set, or the verification-key layout changes in a way that is **not** wire-compatible with the currently deployed contract.

If the release has only client-side changes (UI, Nostr, Blossom, etc.) **do not use this document** — use the standard version bump flow only.

This document assumes the contract changes have already landed on `main` as merged code (e.g. Phases 0–10 of the UpdateCircuit binding fix are merged but the testnet/mainnet contract on the network is still running the *old* ABI).

---

## 0. Decide the target network

- **Testnet-only release** (dev builds, beta, F-Droid preview): keyset may be generated by `scripts/generate-keyset.sh` locally.
- **Mainnet release**: keyset **must** come from a real MPC trusted-setup ceremony — never a local dev keyset. Stop here if you have not run the ceremony.

Record the decision in the PR description and in the GitHub Release notes.

## 1. Version & SemVer

Breaking core changes are a **minor** bump on a pre-1.0 product or a **major** bump on a 1.0+ product. Patch bumps are not valid.

```bash
./scripts/sync-versions.sh 1.3.0            # auto-increments versionCode / CURRENT_PROJECT_VERSION
```

`sync-versions.sh` updates:
- `clients/android/StellarChat/app/build.gradle.kts` (`versionName`, `versionCode`)
- `clients/ios/StellarChat/project.yml` (`MARKETING_VERSION`, `CURRENT_PROJECT_VERSION`)
- `deploy/website/altstore-source.json` (prepends a new version entry)

The iOS `project.pbxproj` is generated from `project.yml` by `xcodegen` (run by CI and locally before opening Xcode) and is not tracked in git — no manual edit.

Commit as its own changeset:
```
chore: bump to 1.3.0 (31) for <short reason>
```

## 2. Contract artefacts

- [ ] WASM builds clean: `stellar contract build --manifest-path contracts/sep-xxxx/Cargo.toml`
- [ ] All circuit VKs (membership + update, per tier) are present under `keysets/keyset-v<N>/`
- [ ] Keyset version bumped if the VK set changed in an incompatible way (clients pin the keyset directory name)
- [ ] `docs/sep.md` version is updated and matches the deployed ABI
- [ ] `docs/cross-platform-test-vectors.json` version bumped; test vectors match the WASM being shipped

## 3. Deploy the contract

### Testnet
```bash
IDENTITY=sep-xxxx-testnet-deployer ./scripts/deploy_sep_xxxx_testnet.sh
```

### Mainnet
```bash
IDENTITY=my-mainnet-deployer ./scripts/deploy-mainnet.sh
```

After deploy, capture the new contract ID (`C…`). This becomes the single source of truth for all clients in this release.

- [ ] Contract ID recorded
- [ ] Per-tier VKs initialised on-chain (membership + update)
- [ ] Smoke test: `create_group` → `update_commitment` → `verify_membership` against the new contract with a fresh group
- [ ] Smoke test: old-ABI call against new contract **fails cleanly** (not panic / silent success)

## 4. Propagate the contract ID to clients

Clients pick up the contract ID from `.env` / `relayer/.env` at build time (see `.github/workflows/release.yml:118-165` for iOS and `clients/android/StellarChat/app/build.gradle.kts:40-71` for Android). Do **not** hand-edit `RelayerDefaults.generated.swift` — it is generated and `.gitignore`d.

- [ ] Update `relayer/.env.example` → `RELAYER_CONTRACT_ID=<new C…>`, `RELAYER_RPC_URL=<endpoint>`
- [ ] Update `.env.example` → `DOMAIN=` (if the Nostr/Blossom/relay domain changed)
- [ ] If mainnet: update CI secrets (repository → Settings → Secrets) with the mainnet values
- [ ] If the app bundles any keyset resources (e.g. `clients/ios/StellarChat/StellarChat/Resources/keyset-v1` referenced from `project.yml:22-24`), bump the bundled folder to the new keyset version and update the path in `project.yml`

## 5. Docs

- [ ] `docs/sep.md` ABI and version are correct
- [ ] Upgrade/migration note added to the release notes explaining that the old contract ID is abandoned
- [ ] `docs/proof-of-soundness.md` updated if circuits changed
- [ ] Vuln / postmortem docs cross-linked if this release is the remediation

## 6. Tests (local)

Only run the affected tests — never the full suite.

- [ ] Rust unit tests for the changed modules: `cargo test -p <crate> <test-path>`
- [ ] Swift tests for touched modules only: `xcodebuild test -only-testing:… -derivedDataPath /tmp/stellar-chat-release-test …`
- [ ] Kotlin JVM tests for touched modules only: `./gradlew :app:testFdroidDebugUnitTest --tests '…'`
- [ ] Cross-platform test vectors round-trip on both clients

## 7. Pre-flight

- [ ] `git status` clean, `git log --oneline` shows the expected version-bump commit as HEAD
- [ ] Working branch is up to date with `origin/main`
- [ ] No uncommitted keyset / `.env` files staged accidentally

## 8. Trigger the Release workflow

Tag pushes no longer trigger the release — only `workflow_dispatch`.

```bash
gh workflow run Release -f tag=v1.3.0
gh run watch   # optional
```

The workflow runs: `android-test` → `ios-test` → `create-release` → `android-build` → `ios-build` → AltStore source update push.

## 9. Post-release

CI pushes its own commit to update `deploy/website/altstore-source.json`. Before any further local pushes:
```bash
git pull --rebase origin main
```

- [ ] GitHub Release has signed APK and IPA artefacts attached
- [ ] AltStore source JSON is updated on the website (the CI push landed)
- [ ] A fresh install from AltStore and F-Droid points at the new contract ID (verify by checking logs for `[OnChain] configured … contractID=C…`)
- [ ] Smoke test an end-to-end group create / update from a clean install on each platform
- [ ] Old installs on the prior contract ID fail gracefully with an actionable error (not a crash) — if not, hotfix the client-side error handling before announcing

## 10. Comms

- [ ] Release notes call out the breaking change and the new contract ID
- [ ] If this closes a vulnerability: link the vuln + postmortem in the release notes and in the GitHub Security Advisory (if published)
- [ ] Users on old versions are instructed to upgrade — their previous groups bound to the old contract cannot be migrated automatically unless a migration tool shipped with this release

## Rollback

You cannot roll back a deployed contract. Rollback means:
1. Cut a new app release that points at the **previous** contract ID (the one from before step 3).
2. Leave the new contract ID deployed but unreferenced until the defect is fixed and a subsequent release points clients back at it.

There is no in-place downgrade path for users on the new client — a build that was shipped pointing at contract `C_NEW` cannot be silently retargeted at `C_OLD`.

---

## Non-breaking client-only release (for contrast)

If this checklist feels heavy because the change is actually client-only:

1. `./scripts/sync-versions.sh 1.2.21`
2. Commit
3. `gh workflow run Release -f tag=v1.2.21`
4. `git pull --rebase origin main` after CI finishes

No contract deploy, no `.env` edits, no keyset changes.
