
---

## Simple Summary

An extension to the SEP-XXXX private group system that enables end-to-end encrypted 1:1 voice and video calls between group members. Call signaling travels over the existing Nostr relay infrastructure as encrypted group events. Media transport uses WebRTC, which provides NAT traversal, codec negotiation, and jitter buffering out of the box. Caller identity is verified using the existing KeyAttestation (BLS12-381 ↔ Ed25519 binding) and DTLS fingerprint pinning.

---

## Motivation

StellarChat supports encrypted text, image, video, and voice messages. All are store-and-forward: the sender publishes an encrypted event, relays hold it, and the recipient decrypts when online. Real-time voice and video calls require a fundamentally different transport — low-latency, peer-to-peer media streams with sub-200ms round-trip delivery.

Building a custom QUIC + codec stack from scratch would require years of engineering to reach the reliability of existing solutions. WebRTC is an open standard (RFC 8825) implemented natively on iOS (`RTCPeerConnection` via GoogleWebRTC / WebRTC.framework) and Android (`org.webrtc`), providing:

- ICE/STUN/TURN for NAT traversal (the #1 cause of P2P call failure)
- DTLS-SRTP for media encryption
- Opus codec with jitter buffer and echo cancellation
- VP8/VP9/H.264 for video
- Bandwidth estimation and adaptive bitrate

The missing piece is **signaling** — exchanging SDP offers/answers and ICE candidates between peers. This proposal uses the existing Nostr encrypted group channel for signaling, keeping relays blind to call metadata.

---

## Design Principles

1. **Reuse existing infrastructure.** Signaling over Nostr (kind 44114 group events). Identity verification via KeyAttestation. Group membership via SEP-XXXX. No new servers or protocols.
2. **Relays remain dumb.** Relays see opaque encrypted events. They cannot distinguish a call signaling event from a chat message — both are kind 44114 with `sep_topic` tags.
3. **No identity leakage.** Caller and callee BLS pubkeys are inside ciphertext. DTLS fingerprints are exchanged inside the encrypted signaling channel, not visible to relays or TURN servers.
4. **WebRTC handles the hard parts.** NAT traversal, codec negotiation, echo cancellation, jitter buffering, bandwidth estimation. No custom media pipeline.
5. **Start with 1:1.** Group calls (mesh or SFU) are a future extension. 1:1 calls are the minimum viable feature.

## Specification

### 1. Call Signaling Protocol

Call signaling messages are sent as version 2 group messages (kind 44114) with `"type": "call"`. They travel through the same encrypted Nostr channel as chat messages and are indistinguishable to relays.

#### 1.1 Signaling Message Format

```json
{
  "v": 2,
  "type": "call",
  "senderBlsPubkey": "<base64>",
  "ts": 1712000000,
  "call": {
    "action": "<offer|answer|ice|hangup|busy|reject>",
    "callId": "<random 32-byte hex>",
    "sdp": "<SDP string, present for offer/answer>",
    "candidate": "<ICE candidate string, present for ice>",
    "sdpMid": "<SDP media ID, present for ice>",
    "sdpMLineIndex": "<int, present for ice>",
    "mediaType": "<audio|video>"
  }
}
```

Fields:

- `call.action` — the signaling action (see §1.2)
- `call.callId` — a unique identifier for this call session. Generated by the caller as 32 random bytes (hex-encoded). All signaling messages for the same call share this ID.
- `call.sdp` — the SDP offer or answer string. Present only for `offer` and `answer` actions.
- `call.candidate` / `call.sdpMid` / `call.sdpMLineIndex` — ICE candidate details. Present only for `ice` actions.
- `call.mediaType` — `"audio"` for voice-only calls, `"video"` for video calls. Present in `offer`.

#### 1.2 Signaling Actions

| Action | Direction | Description |
|--------|-----------|-------------|
| `offer` | Caller → Callee | SDP offer with media type. Initiates a call. |
| `answer` | Callee → Caller | SDP answer accepting the call. |
| `ice` | Bidirectional | Trickle ICE candidate. Multiple per session. |
| `hangup` | Bidirectional | End an active call or cancel a pending offer. |
| `busy` | Callee → Caller | Callee is already in another call. |
| `reject` | Callee → Caller | Callee explicitly declined. |

#### 1.3 Call State Machine

```
                    ┌─────────┐
         offer      │         │  hangup/timeout
    ┌──────────────►│ Ringing ├──────────────┐
    │               │         │              │
    │               └────┬────┘              │
    │                    │ answer             │
    │               ┌────▼────┐              │
    │               │         │  hangup      │
    │               │ Active  ├──────────────┤
    │               │         │              │
    │               └─────────┘              │
┌───┴───┐                              ┌────▼────┐
│ Idle  │◄─────────────────────────────│  Ended  │
│       │  busy/reject/timeout         │         │
└───────┘                              └─────────┘
```

State transitions:

- **Idle → Ringing**: On sending or receiving an `offer`.
- **Ringing → Active**: On receiving `answer` (caller side) or sending `answer` (callee side).
- **Ringing → Ended**: On `hangup` (cancel), `busy`, `reject`, or timeout (30 seconds with no answer).
- **Active → Ended**: On `hangup` from either party, or ICE connection failure.
- **Ended → Idle**: Automatic after cleanup.

#### 1.4 Timeout Rules

- **Ring timeout**: 30 seconds. If no `answer`, `busy`, or `reject` is received, the caller sends `hangup` and transitions to Ended.
- **ICE timeout**: 15 seconds. If the ICE connection state remains `failed` or `disconnected` for 15 seconds during an active call, both parties hang up.
- **Stale signaling**: Signaling messages with `ts` older than 60 seconds MUST be ignored to prevent replay of old offers.

### 2. Call Encryption

#### 2.1 Signaling Encryption

Call signaling messages are encrypted exactly like chat messages: AES-256-GCM with the group message key derived from `HKDF(groupSecret || epoch || salt)`. This means:

- All group members can observe that a call is happening (they can decrypt the signaling).
- Only the two call participants exchange DTLS keys and establish the media session.
- This is consistent with the group privacy model — group members already see each other's messages.

For 1:1 groups (direct messages), only the two members can decrypt signaling, providing full privacy.

#### 2.2 Media Encryption

WebRTC provides DTLS-SRTP encryption by default. The DTLS handshake establishes per-session symmetric keys for media encryption. This provides:

- **Forward secrecy**: Each call session has ephemeral DTLS keys. Compromising one session does not compromise others.
- **Independence from group key**: Media encryption keys are not derived from the group secret. A compromised group secret does not expose recorded media streams.

#### 2.3 Identity Verification via DTLS Fingerprint Pinning

To prevent a TURN server or network attacker from performing a MITM attack on the DTLS handshake:

1. The caller includes their DTLS fingerprint in the `offer` SDP (standard WebRTC behavior).
2. The callee includes their DTLS fingerprint in the `answer` SDP.
3. Both parties verify that the remote DTLS fingerprint received during the DTLS handshake matches the fingerprint from the signaling message.

Since the signaling channel is end-to-end encrypted (AES-256-GCM with the group key) and sender identity is verified via `senderBlsPubkey` (which is bound to a Stellar Ed25519 key via KeyAttestation), the DTLS fingerprints are authenticated. A TURN relay cannot substitute its own fingerprint without breaking the signaling encryption.

This provides **end-to-end encryption verification** without requiring a separate key verification ceremony (like Signal's safety numbers).

### 3. WebRTC Configuration

#### 3.1 ICE Servers

Clients SHOULD use at least one STUN server and one TURN server for reliable connectivity:

```
STUN: stun:stun.l.google.com:19302  (or self-hosted)
TURN: turn:<self-hosted>:3478        (UDP + TCP fallback)
```

TURN server credentials can be distributed via the group channel or configured per-deployment. For privacy, self-hosted TURN servers are strongly recommended — public TURN providers can observe media relay metadata.

#### 3.2 Codec Preferences

| Media | Codec | Bitrate | Channels | Sample Rate |
|-------|-------|---------|----------|-------------|
| Audio | Opus | 32 kbps (voice) | 1 (mono) | 48 kHz |
| Video | VP8 or H.264 | 500 kbps–2 Mbps (adaptive) | — | — |

Opus is mandatory for audio. Video codec is negotiated via SDP — prefer VP8 for open-source consistency, fall back to H.264 for hardware acceleration.

#### 3.3 RTCPeerConnection Configuration

```
iceTransportPolicy: "all"       // Use both STUN and TURN
bundlePolicy: "max-bundle"      // Multiplex audio+video on one port
rtcpMuxPolicy: "require"        // Require RTCP multiplexing
sdpSemantics: "unified-plan"    // Modern SDP format
```

### 4. Platform Integration

#### 4.1 iOS — CallKit

CallKit integration is required for incoming call notifications when the app is backgrounded or killed.

```
CXProvider — reports incoming/outgoing calls to the system
CXCallController — programmatic call actions (answer, end, mute)
CXProviderDelegate — handle system events (call answered from lock screen)
```

Flow:
1. On receiving an `offer` event → report incoming call via `CXProvider.reportNewIncomingCall()`
2. User answers → CallKit notifies delegate → send `answer` signaling → establish WebRTC
3. User declines → send `reject` signaling
4. Call ends → `CXProvider.reportCall(ended:)`

CallKit also handles:
- Audio session management (route to speaker/earpiece/Bluetooth)
- Call interruption (another phone call incoming)
- Lock screen call UI

**Info.plist** requirement:
```xml
<key>UIBackgroundModes</key>
<array>
    <string>voip</string>
</array>
```

#### 4.2 Android — ConnectionService + Telecom Framework

```
ConnectionService — system call management
Connection — represents one call with state transitions
TelecomManager — register phone account, place calls
```

Flow:
1. On receiving an `offer` event → `TelecomManager.addNewIncomingCall()`
2. User answers → `Connection.onAnswer()` → send `answer` signaling → establish WebRTC
3. User declines → `Connection.onReject()` → send `reject` signaling
4. Call ends → `Connection.setDisconnected()`

**AndroidManifest.xml** requirements:
```xml
<uses-permission android:name="android.permission.MANAGE_OWN_CALLS" />
<uses-feature android:name="android.hardware.telephony" android:required="false" />

<service android:name=".call.CallConnectionService"
    android:permission="android.permission.BIND_TELECOM_CONNECTION_SERVICE">
    <intent-filter>
        <action android:name="android.telecom.ConnectionService" />
    </intent-filter>
</service>
```

#### 4.3 Push Notifications for Incoming Calls

For incoming calls when the app is not running, a push notification mechanism is required:

- **iOS**: VoIP push via APNs (`PushKit` with `PKPushTypeVoIP`). VoIP pushes launch the app in the background and MUST immediately report a call via CallKit — failure to do so will cause Apple to terminate the app.
- **Android**: FCM high-priority data message. The `FirebaseMessagingService` receives the notification and triggers `TelecomManager.addNewIncomingCall()`.

The push notification payload should be minimal and opaque — it signals "you have an incoming call" without exposing caller identity. The actual signaling (SDP offer, caller BLS pubkey) is retrieved from the Nostr relay upon waking.

**Note**: Push notification delivery requires a notification relay service that bridges Nostr events to APNs/FCM. This service sees only the delivery token and a hashed topic — not the call content. Design of this service is out of scope for this document but MUST follow the same blindness principles as Nostr relays.

### 5. Audio Session Management

- `MODE_IN_COMMUNICATION` enables acoustic echo cancellation

## Security Considerations

### Signaling Privacy

Call signaling is indistinguishable from chat messages at the relay layer — both are kind 44114 events with `sep_topic` tags, encrypted with the group key. A relay operator cannot determine whether a group is exchanging messages or establishing a call.

### TURN Server Metadata

If a call routes through a TURN server, the TURN server can observe:
- IP addresses of both peers
- Call duration (from relay allocation lifetime)
- Bandwidth (from relayed bytes)

It **cannot** observe:
- Call content (DTLS-SRTP encrypted)
- Caller/callee identity (DTLS fingerprints exchanged inside E2E-encrypted signaling)
- Group membership

Self-hosted TURN servers mitigate this metadata exposure.

### Overbilling Attack

A malicious group member could spam `offer` events to trigger ring notifications. Mitigation:
- Rate-limit incoming offers: max 1 per sender per 10-second window
- Ignore offers from `senderBlsPubkey` values not in the current member set
- Auto-reject after 3 consecutive unanswered offers from the same sender within 5 minutes

### Replay Protection

- Signaling messages with `ts` older than 60 seconds are rejected
- Each `callId` is used once; duplicate `callId` with `offer` action is ignored after the first
- ICE candidates for an unknown or ended `callId` are ignored

### Forward Secrecy

Call media has forward secrecy via DTLS ephemeral keys — each call generates fresh symmetric keys. This is strictly stronger than the chat encryption model (which has no forward secrecy per N-20).

## Implementation Phases

### Phase 1: 1:1 Audio Calls (MVP)

**Goal**: Voice calls between two members of a 1:1 group.

1. Add WebRTC dependency (SPM for iOS, Maven for Android)
2. Implement call signaling message parsing in `NostrMessageTransport` (new `"type": "call"` handler)
3. Build `CallManager` actor/class — owns `RTCPeerConnection`, manages call state machine
4. Build call UI — incoming/outgoing/active screens
5. Integrate CallKit (iOS) / ConnectionService (Android)
6. Configure STUN/TURN servers
7. Test on physical devices across NAT boundaries

### Phase 2: Video Calls

**Goal**: Add video track to existing call infrastructure.

1. Add camera capture (`RTCCameraVideoCapturer`)
2. Add video rendering (`RTCMTLVideoView` on iOS, `SurfaceViewRenderer` on Android)
3. Add camera controls (flip, on/off)
4. Update call UI with local/remote video views
5. Handle `mediaType: "video"` in signaling

### Phase 3: Group Calls (Future)

**Goal**: Multi-party calls for groups with 3+ members.

This requires either:
- **Mesh topology**: Each participant connects to every other (works for 3-4 people, O(n^2) bandwidth)
- **SFU (Selective Forwarding Unit)**: Server that receives one stream per sender and forwards to all others (scales to 20+ participants but requires infrastructure)

An SFU is recommended for groups larger than 3. Design of the SFU is out of scope for this document.

### Phase 4: Push Notifications (Future)

**Goal**: Incoming call notifications when the app is not running.

Requires a notification relay service that watches Nostr events and bridges to APNs/FCM. Design should follow the existing relay blindness model.
