## 3. Proof / replay protection (nullifier scoping, used-proof keys)

- **L727–733 (`proof_hash`)**: Hash is `sha256(a || b || c)` over the *raw proof bytes only*. ⚠️ **Critical scoping issue**: the hash does not include `group_id`, `epoch`, the public inputs, or a domain separator. Implications:
  - A proof valid for group A at epoch N cannot be replayed at group B even if both have the same `commitment` and `epoch`, because `verify_membership_proof` will only succeed when the public inputs match the stored state. **However**, two distinct logical operations (e.g., `create_group` for group X and `verify_membership` for some other group, both with proofs that happen to verify) would have distinct proof bytes, so collision is cryptographically negligible — *but* the design fragility is real: any future code path that re-uses a proof against multiple verifier paths is silently a double-use.
  - More concretely: `verify_membership` (read-only, L583–597) does **not** call `check_proof_replay` or `record_proof`. A prover can submit the same proof to `verify_membership` repeatedly. ✓ acceptable for read-only.
  - But **`deactivate_group` (L600) and `update_commitment` (L516)** both consume proof hashes from the same global `UsedProof` namespace. A proof crafted for `update_commitment` and used there cannot be replayed for `deactivate_group` (good), but the converse — a proof valid for both circuits' public input shape — is impossible because membership and update VKs differ. Practically safe, theoretically fragile.
- **L735–745 (`record_proof`)**: TTL is bumped to ~30 days. ⚠️ **Replay window**: after ~30 days, a `UsedProof` entry can be archived. If the same proof bytes are resubmitted after archival, `check_proof_replay` returns Ok and the proof can be re-used. For `update_commitment` this is largely benign because the public inputs must match the *current* `c_old` and `epoch_old`, which advance on every update — a stale proof won't pass `PublicInputsMismatch`. **However, for `create_group`, the public inputs are unconstrained by prior state** (epoch=0, commitment chosen by caller). A creator can build a proof, create a group, deactivate it, wait 30+ days, and re-create another group with the same proof bytes for a different `group_id`. Given `MAX_GROUPS_PER_TIER` is enforced, the impact is limited, but the proof-of-knowledge claim is undermined. Recommend including `group_id` (and ideally `epoch`) in the proof hash preimage.
- **L600–650 (`deactivate_group`)**: Calls `check_proof_replay` and `record_proof`. ✓ Good — prevents replaying the same deactivation proof, though deactivation is already idempotent due to `GroupInactive` check.

## Top 3 highest-impact fixes

1. **Scope `UsedProof` keys to `(group_id, proof_hash)` and include public inputs / epoch in the preimage (§3).** The current global namespace plus 30-day TTL means a `create_group` proof can be replayed against a fresh `group_id` after archival, weakening the proof-of-knowledge guarantee. ## 1. Authorization & access control (require_auth, admin gating, restricted mode)

- **Lines 376-388 (`update_commitment`)**: No `caller.require_auth()` is taken. The comment justifies this by claiming the Groth16 proof IS the authorization. While defensible, this means **any address can submit any valid proof on behalf of the group, including front-runners.** A relayer/MEV actor observing a proof in the mempool can replay-front-run it (the nullifier check below will then make the original prover's tx fail with `ProofReplay`). Recommend adding an optional `caller: Address` parameter requiring auth, OR binding the caller's address into the proof's public inputs at the circuit level.
- **Lines 449-485 (`deactivate_group`)**: Same pattern; "any current member may deactivate" is irreversible and any observer of a membership proof can race-front-run a legitimate user to permanently freeze the group. This is more dangerous than `update_commitment` because the action is irreversible. Strongly recommend binding caller into the proof or requiring `caller.require_auth()` plus circuit-level binding.
- **Lines 318-329 (`create_group`)**: Restricted-mode check correctly compares `caller != admin` and `caller.require_auth()` is taken at line 313. ✓

## 2. Storage tier choice (persistent / instance / temporary) and TTL handling

- **Line 203 (`UsedProof`)**: Used-proof nullifiers are stored in **persistent** storage with TTL bump on write. Once a nullifier's TTL expires and it gets evicted, an attacker can replay the same proof. For a system whose security model rests on nullifier durability, this is fragile. **Recommend either (a) tying nullifier lifetime to group lifetime via explicit re-bumps on every group update, or (b) acknowledging in design docs that nullifiers are valid only within ~30 ledger-day windows.** See `record_proof` (lines 600-607).

## 3. Proof / replay protection (nullifier scoping, used-proof keys)

- **Lines 593-599 (`proof_hash`)**: The replay-protection key is the SHA-256 of the raw Groth16 proof bytes (A, B, C). **This is global across all groups and all entrypoints (create_group, update_commitment, deactivate_group, verify_membership* — wait, `verify_membership` does not check replay, which is correct since it's read-only).** Critical issues:
  1. **A valid proof for group X cannot be replayed for group Y because public inputs differ — pairing check fails.** Cross-group replay is therefore prevented by the verifier itself, not by the nullifier. ✓
  2. **However, a Groth16 proof is randomized (the prover injects fresh randomness r, s)**. An honest user who legitimately wants to re-verify the same statement in a new group could simply re-prove. The nullifier on proof bytes is therefore a **proof-bytes anti-front-running tool, not a true logical nullifier.** A front-runner who replays the exact bytes will hit `ProofReplay`, but a malicious prover holding the secret can re-randomize and bypass.
- **Missing scoping**: The nullifier key contains no `group_id` or `epoch` binding. If `record_proof` storage ever evicts (TTL), the proof bytes can be reused. Recommend hashing `(group_id, epoch, proof)` instead of just `proof`. (Line 594)
- **`deactivate_group` consumes the nullifier (line 471) but `update_commitment` ALSO consumes a nullifier with different public inputs.** A legitimate prover cannot use the same proof for both since public inputs differ — but a user wanting to deactivate after a recent update may need a fresh proof. This is fine but worth documenting.
- **`verify_membership` (lines 414-437) correctly does NOT call `check_proof_replay` / `record_proof`**, so read-only verification cannot poison the nullifier set. ✓
